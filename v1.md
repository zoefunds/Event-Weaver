# EventWeaver V1

## Purpose

V1 moves EventWeaver's staking and payout rail from native GEN to test USDC on Base Sepolia. GenLayer remains the source of truth for market rules, positions, evidence-driven adjudication, fees, and payout calculations. Base Sepolia holds the USDC and executes user deposits, settlement allocations, and claims.

This split gives users a familiar stablecoin reserve while retaining GenLayer's decentralized intelligent-contract resolution.

## Architecture

```text
User wallet
  |\
  | \ Base Sepolia: approve USDC, stake(marketId, side, amount), claim
  |  \
  |   EventWeaverEscrow
  |       |
  |       | Staked(marketId, staker, side, amount) event
  |       v
  |   Backend stake relay  ------ confirms deposit, then calls -----+
  |       ^                                                         |
  |       | settlement transaction (settle)                        v
  |   Backend API, indexer, resolver, relayer, stake relay --> record_stake(...)
  |       |                                                         |
  |       | reads final outcomes and payout allocations             |
  |       v                                                         v
  +----> GenLayer EventWeaver intelligent contract <----------------+
          create market, record YES/NO position (relayer-only), resolve evidence, calculate payouts
```

The backend has a narrowly scoped relayer key used for two calls only: escrow `settle` on
Base Sepolia and `record_stake` on GenLayer. It cannot transfer USDC out of the escrow except
through the contract's predefined settlement mechanism, and it cannot record a stake it hasn't
independently observed as a confirmed deposit. A user always claims their own payout directly
from the escrow contract.

**Why staking goes through the relayer instead of the user's own wallet calling GenLayer
directly:** an earlier version of V1 let the wallet call `stake_yes`/`stake_no(marketId,
amount)` itself, trusting whatever `amount` it claimed — with no check that any USDC had
actually moved, and no recovery if the escrow deposit succeeded but that second call never
landed. `record_stake` closes both gaps; see [review-v1.md](review-v1.md) for the full
before/after.

## User lifecycle

1. A creator defines a causal-chain market on GenLayer with conditions, public evidence URLs, a deadline, and a confidence floor.
2. A participant selects YES or NO and enters a USDC amount.
3. The wallet approves USDC and calls `EventWeaverEscrow.stake(marketId, side, amount)` on Base Sepolia — `side` (1 = YES, 2 = NO) travels with the deposit itself. This is the only on-chain action the user performs to stake.
4. The backend's stake relay observes the `Staked` event once it clears confirmations, records it in Postgres, and calls `record_stake(marketId, staker, side, amount, base_tx_hash)` on GenLayer — the only call GenLayer accepts to create a position. If this call fails (crash, RPC hiccup), the relay keeps retrying the same row until it succeeds; `base_tx_hash` makes retries idempotent. Poll `GET /api/stakes/:txHash` to watch a deposit move from `confirmed_onchain`/`retry_pending` to `applied`.
5. At or after the deadline, the resolver requests adjudication. GenLayer validators inspect the declared evidence and publish the terminal result.
6. The backend relayer reads `get_base_payouts(marketId)` from GenLayer and calls escrow `settle` once for that market.
7. A winner calls escrow `claim(marketId)` through the frontend. USDC transfers directly to that wallet.

## Contract responsibilities

### GenLayer intelligent contract

- Owns market metadata, causal-chain steps, evidence reasoning, deadline state, position ledger, terminal outcome, fee calculations, and the final Base payout list.
- Provides `get_base_payouts(marketId)` for the relayer after terminal resolution.
- `record_stake(marketId, staker, side, amount, base_tx_hash)` is relayer-only and the sole way a `Position` is created; `applied_base_tx` tracks consumed deposit hashes so a retried call is a safe no-op.
- Does not custody USDC and does not send native GEN as a payout in V1.
- Uses its internal authenticated time source. Public methods do not accept caller-controlled timestamps.

### Base Sepolia EventWeaverEscrow

- Accepts USDC deposits with `stake(marketId, side, amount)` — `side` is part of the deposit, not a separate unauthenticated message.
- Tracks a deposited amount, allocated amount, and settlement state per market.
- Allows the authorized relayer to call `settle(marketId, recipients, amounts)` once.
- Allows any recipient with an allocation to call `claim(marketId)`.
- Exposes `claimable(marketId, account)` as the live source of truth for a user payout.

## Frontend behavior

- Market creation and adjudication use the GenLayer wallet client directly.
- USDC approval, deposit (with side), and claim use the injected EIP-1193 wallet on Base Sepolia. The wallet never calls GenLayer to record a stake — after the deposit confirms, the UI polls `GET /api/stakes/:txHash` while the backend relay applies it.
- Base Sepolia transaction gas is explicitly bounded to avoid an RPC gas-estimation response that exceeds Base Sepolia's maximum transaction gas limit.
- Claim actions wait for the Base Sepolia transaction receipt before reporting success.
- Portfolio and market detail pages read Base escrow claimability through the backend. The claim button only appears when the live escrow amount is greater than zero.
- After a successful claim, the portfolio refreshes and the claim action disappears.

## Backend operations and reliability

The backend has five independent duties: serve indexed API reads, mirror GenLayer market data to Postgres, request adjudication for due markets, relay confirmed USDC deposits into GenLayer positions, and relay final Base payouts.

StudioNet uses a shared, rate-limited RPC. V1 therefore uses five-minute polling for the indexer, deadline resolver, and Base settlement scan; the stake relay polls Base Sepolia (a separate RPC) on a faster cycle since it isn't subject to that cap. The portfolio endpoint caches each address for 60 seconds. If a fresh StudioNet read is rate-limited, a previously cached portfolio is returned with `stale: true` instead of returning an error page.

The live Base escrow claim balance is still included in portfolio results, so an already confirmed USDC claim is not shown again merely because GenLayer retains a historical payout quote.

BASE_SEPOLIA_RPC_URL=https://sepolia.base.org
BASE_SEPOLIA_USDC=0x036CbD53842c5426634e7929541eC2318f3dCF7e

## Verification checklist

1. `GET /health` reports `ok: true` and the V1 GenLayer contract address.
2. The frontend bundle contains the V1 GenLayer contract, Base escrow, API URL, and USDC address.
3. A stake produces a USDC approval and escrow deposit (with side) on Base Sepolia; `GET /api/stakes/:txHash` moves from `confirmed_onchain`/`retry_pending` to `applied` without any further wallet action, and a matching GenLayer YES or NO position appears.
4. Calling `record_stake` from any address other than the configured relayer reverts (see the direct test suite).
5. Replaying the same `base_tx_hash` through `record_stake` does not change the position or pool totals (idempotency / crash-recovery proof).
6. A terminal market shows an escrow pool with `settled: true` after the relayer scan.
7. `claimable(marketId, wallet)` is greater than zero before a winning claim and zero after it.
8. The wallet's Base Sepolia USDC balance rises by the claimed amount.
9. Portfolio and market detail no longer display a claim button once `claimable` is zero.

## Migration and compatibility

V1 is not compatible with legacy native-GEN markets or the retired GenLayer deployment. Existing historical data should be treated as archival only. New V1 markets must use the deployed V1 GenLayer contract, V1 Base escrow, and the configuration listed above.
